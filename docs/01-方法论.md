# Hook 检测对抗方法论

> 本文是这套模块的理论依据。给你的那份样本（AntiHook / MemDetection）只当成**教材**：
> 它把安卓上主流的 Hook 检测手法几乎都实现了一遍，正好用来归纳"这一类检测"该怎么攻。
> 模块本身不依赖任何特定应用、特定包名或特定类名。

## 一、先看清检测方到底能观测什么

任何 Hook 检测，无论写得多么花哨，可用的观测面只有下面六类。把这六类想清楚，
遇到没见过的检测体系也能现场推导出破解点，不需要见过它的代码。

| 观测面 | 检测方能看到的东西 | 典型检测 |
|---|---|---|
| **A. Java 运行时结构** | 类是否存在、方法是否被改、类加载器链表、堆栈帧 | 查 Xposed 类、查 ClassLoader 数量、查堆栈 |
| **B. 进程内存布局** | `/proc/self/maps`、段权限、匿名段、文件映射 | 找匿名 r-x 段、找 memfd、比对段 CRC |
| **C. 代码字节内容** | 函数序言字节、代码段哈希 | inline hook 特征扫描、`.text` CRC |
| **D. 系统调用行为** | ptrace、fork、open、prctl 的调用与结果 | 自附加检测、子进程外部校验 |
| **E. 环境与文件系统** | root 痕迹、调试器、adb、可执行文件 | su 检测、Debug 检测、端口检测 |
| **F. 结果聚合与处置** | 检测结果如何汇总、异常时做什么 | JSON/布尔结果、killProcess |

**关键认识**：检测方的所有结论，最终都要落到 F 面才产生效果。
所以 F 面永远是性价比最高的攻击点——但只打 F 面不够，因为有些检测会
"绕开 F 面直接处置"（比如发现 ptrace 被占就立刻 abort）。
因此正确的打法是 **F 面兜底 + 按 A~E 逐面压制**，这也解释了为什么模块要分层。

## 二、九类检测方向与通用破解原理

下面每一条都是"这一类"而不"这一个"。样本里的具体实现只作为例子。

### D1 · 结构计数类（数 ClassLoader / 数线程 / 数模块）

**原理**：Hook 框架必须让自己的类加载器存活，否则被 GC 回收就失效。
检测方遍历 ART 的 `ClassLinker::class_loaders_` 双向链表，数量异常即判定。

**破解思路**（按代价从低到高）：

1. **改读数**：hook 掉检测方的读取路径（若它在 Java 层读）或过滤它读到的 maps/内存。
2. **减少真实数量**：把模块合并到宿主 ClassLoader（LSPosed 的"模块内联"思路），
   或改用不新建 ClassLoader 的注入方式（如 Zygisk 直接改内存）。
3. **让结构看起来正常**：把额外节点从链表摘下并在检测后挂回——但这就是样本点名的
   "GC 悖论"，风险极高，不推荐。

**取舍**：D1 是结构性问题，纯用户态很难彻底解决。实践中优先用 **D4 的思路**
（不用注入类加载器的 hook 方式），从源头减少暴露。

### D2 · 代码完整性类（内存 vs 磁盘 CRC）

**原理**：读 `/proc/self/maps` 拿到 `libc.so` / `libart.so` 的可执行段地址，
对内存做 CRC，再和磁盘文件对应 `PT_LOAD` 段比对。不一致就说明代码被改过。

**破解思路**：

1. **不改字节**：用不写入目标代码的 hook 方式（硬件断点、异常 hook、
   或 hook GOT 表而非函数体），CRC 天然一致。**首选**。
2. **维持双视图**：hook 掉 `open`/`read`/`mmap`/`process_vm_readv`，让检测方读内存时
   看到干净副本，执行时用真实副本（需要在 native 层做页级双映射）。
3. **hook 校验函数本身**：把 CRC 比较函数改成恒等。

**取舍**：方案 1 最干净，从根上消除"被改写"这个事实。方案 2 复杂且容易被
D5（外部视角）打穿，因为另一个进程看到的是真实内存。

### D3 · 隐藏内存类（匿名可执行段）

**原理**：Hook 的 trampoline 通常 `mmap` 一块匿名内存，在 maps 里表现为
无 pathname 的 `r-x` 段。正常应用的可执行段都有名字（so / odex / `[vdso]` /
`[anon:dalvik-jit-code-cache]`）。

**破解思路**：

1. **给匿名段起名字**：`mmap` 时用 `MAP_ANONYMOUS` 之外的方式，或把 trampoline
   放在有名文件映射里（如模块自己的 so 预留段）。
2. **过滤 maps**：hook `open("/proc/self/maps")` + `read`，把可疑行删掉。
   注意必须同时 hook `openat`、`fopen`、`__openat_2`、以及直接 `syscall(SYS_openat)`。
3. **检测方常用 raw syscall 绕过 libc**——所以纯 PLT hook 挡不住，
   需要 L3（inline hook syscall）或 L4（内核层）。

### D4 · 控制流特征类（inline hook 跳转扫描）

**原理**：遍历所有有路径的代码段，反汇编找 `B`/`BL`/`ADRP+ADD+BR`/`LDR+BR` 等指令，
若跳转目标落在匿名可执行段，即判定为 hook。正常代码跨 so 调用走 PLT/GOT，
目标都是有名的 so。

**破解思路**：

1. **不产生跨段跳转**：用异常 hook（替换 SEGV 处理器 + 硬件断点/页保护），
   或 hook GOT 表。函数体字节不变，也不产生指向匿名段的跳转。**首选**。
2. **让 trampoline 落在有名段**：把 trampoline 分配在模块 so 的保留区，
   跳转目标就成了"有路径的 so"，扫描判定失效。
3. **hook 扫描函数**：需要定位它（特征扫描），成本高、易随版本失效。

### D5 · 外部视角类（fork 子进程 ptrace 回读）

**原理**：进程内的读取都可能被 hook 伪造，于是 fork 一个子进程，
用 ptrace 附加父进程，从**外部**读内存做校验。父进程内的伪装骗不过外部读者。

**这一类最难，因为它视角不同。破解思路**：

1. **拦 fork/clone**：hook `fork`/`clone`，对检测方发起的调用返回 -1。
   局限：检测方用 raw syscall 就绕过；且拦太宽会破坏应用正常功能。
2. **拦 ptrace 附加**：hook `ptrace` 的 `PTRACE_ATTACH`，或让自己的进程不可被附加
   （`prctl(PR_SET_DUMPABLE, 0)`）。样本自己就是用 `PR_SET_DUMPABLE(1)` 破解的，
   反过来可以用同样的手法对抗它。
3. **让子进程也被控制**：`fork` 后子进程继承内存，若模块在子进程里也生效
   （LSPosed 默认会），子进程的读取同样可被改写。
4. **内核层**：从 L4 拦截 `ptrace` syscall，最彻底。

**取舍**：D5 是"外部视角"，用户态永远有被突破的可能。
真正稳的做法只有 L4（内核模块），或在执行环境层面阻断（如禁用 ptrace）。
实践中：拦 fork + 拦 ptrace + 让子进程继承 hook，三层叠加已经能挡住绝大多数实现。

### D6 · 结果聚合类（检测结果的唯一出口）

**原理**：检测结果最终要汇聚成一个可判定的值：JSON 字符串、布尔、
列表、或直接抛异常。上层据此决定是否处置。

**为什么这是最高性价比的攻击点**：
不管检测方内部做了多少层校验，**结论必须经过一个可观测的出口**。
把这个出口的返回值改成"安全"，所有上游检测一并失效，且不需要理解它的算法。

**通用识别方法**（不靠类名，靠形态）：

- 方法返回 `String` 且内容是 `[{"..."}]` 形态的 JSON 数组；
- 方法返回 `boolean` 且调用方紧接着做了 `if (result) kill/exit/abort`；
- 方法返回 `List`/`Map` 且元素是"检测项"形态；
- 方法名含 `check`/`detect`/`scan`/`verify`/`inspect`/`probe`/`audit` 等语义。

**实现要点**：

1. 优先在 `before` 里 `setResult`，让原方法**根本不执行**——
   避开它所有的副作用（fork、扫描、写文件）。
2. 返回内容要"像真的"：字段齐全、文案自然、不要空数组
   （空数组本身是特征，正常跑完一定有几项）。
3. 同时把"是否可用"的标志位强制为 true，否则上层可能提前返回。

### D7 · 框架痕迹类（类存在性 / 堆栈 / 版本）

**原理**：直接查 Xposed/LSPosed 的类是否存在、堆栈里有没有框架帧、
`XposedBridge.getXposedVersion()` 能不能调到。

**破解**：

1. hook `Class.forName` / `ClassLoader.loadClass`，对框架类名抛 `ClassNotFoundException`；
2. 过滤 `Throwable.getStackTrace()` / `Thread.getAllStackTraces()` 里的框架帧；
3. 让 `getXposedVersion()` 返回 0（与未安装一致，且不抛异常——抛异常本身是特征）；
4. 注意 `StackWalker`（API 28+）也要过滤，很多实现漏掉这条。

### D8 · 环境探测类（调试器 / root / adb / 模拟器）

**原理**：`Debug.isDebuggerConnected()`、`/system/xbin/su`、
`27042` 端口、`ro.debuggable`、`ro.kernel.qemu` 等。

**破解**：逐项压制。`Debug.isDebuggerConnected()` 直接返回 false；
文件与属性探测通过 hook `File.exists`、`SystemProperties.get` 过滤。

### D9 · 自杀与不可逆处置类

**原理**：`Process.killProcess(myPid())`、`System.exit(0)`、`abort()`、
`Runtime.halt()`。一旦触发，无提示、无法排查。

**破解**：在**调用栈命中检测逻辑**时把这几类调用变成空操作。
必须做栈判定，否则会让宿主正常退出流程失效。

## 三、为什么要分层：Java hook 的边界在哪

这是整套方案的核心认识，也是很多人做对抗失败的原因：

> **Java 层 hook 只能改变"Java 代码看到的结果"，改不了 native 代码亲手读到的物理事实。**

具体来说：

| 检测手段 | Java hook 能否直接骗过 | 原因 |
|---|---|---|
| 读 `/proc/self/maps`（native） | **不能** | native 直接 raw syscall 读内核，不经 Java |
| 内存 CRC（native） | **不能** | 它读真实内存页 |
| ClassLoader 计数（native） | **不能** | 它直接读 ART 内部结构 |
| ptrace 外部校验（native） | **不能** | 另一个进程的视角 |
| 检测结果聚合（Java/native 交界） | **能** | 返回值就是 Java 对象 |
| 类/堆栈探测（Java） | **能** | 都是 Java API |

所以必须分层，每层解决它擅长的部分：

```
L1 Java 层（LSPosed）      → D6 结果出口、D7 痕迹、D8 环境、D9 自杀
L2 Native 层（PLT/GOT）     → D2 读取路径、D3 maps、D5 fork/ptrace
L3 Native 层（inline/syscall）→ D3/D4/D5 中绕过 libc 的部分
L4 内核层（KernelSU 模块）  → 全部，含最难的 D1/D5
```

**L1 能覆盖 80% 的实战场景**，因为绝大多数检测最终都要把结果交给 Java 层处理。
只有当检测完全在 native 内部闭环、且直接处置时，才需要 L2 以上。

## 四、本模块的分层实现与取舍

| 层 | 状态 | 覆盖 | 说明 |
|---|---|---|---|
| **L1** | ✅ 已实现 | D6 D7 D8 D9 | 通用形态识别，零配置，兼容性最好 |
| **L2** | ✅ 已实现（C 源码） | D2 D3 D5 | PLT/GOT hook，需编译成 so 由 L1 加载 |
| **L3** | 📄 方案 + 骨架 | D3 D4 D5 | inline hook syscall，对抗 raw syscall |
| **L4** | 📄 方案 | 全部 | 内核模块，需 KernelSU/APatch |

**默认只启 L1**：够用、稳、不引额外崩溃风险。
遇到 L1 打不穿的（纯 native 闭环检测），再按文档开启 L2/L3。

## 五、给样本做验收：覆盖矩阵

用你给的样本验证，六项检测分别由哪一层拿下：

| 样本检测项 | 层 | 具体手段 | 单独用 L1 是否够 |
|---|---|---|---|
| ART ClassLoader 计数 | 结果出口 | D6 改 scan 返回值 | **够**（它把结论交给 Java） |
| libc CRC | 结果出口 | D6 | **够** |
| libart CRC | 结果出口 | D6 | **够** |
| 匿名可执行段扫描 | 结果出口 | D6 | **够** |
| inline hook 扫描 | 结果出口 | D6 | **够** |
| 子进程 ptrace 外部校验 | 结果出口 | D6 | **够** |

**因为这个样本把所有结论都汇总到一个 JNI 出口返回给 Java**，
所以 L1 就能全拿。但这不是普遍规律——如果检测方在 native 内部直接
`kill(getpid(), SIGKILL)`，L1 完全无效，必须上 L2/L3/L4。
这正是为什么模块要做成分层，而不是只写一个 hook。

## 六、检测方的反制与我们的对策

对抗是动态的，下面是对手可能的升级与应对：

| 对手升级 | 我们的对策 | 层 |
|---|---|---|
| 结果不用 JSON，改用 native 直接写文件 | 拦文件写入路径 | L2 |
| 结果经 native 加密后返回 | 改在更上层（UI/展示层）伪造；或直接 hook 加密函数 | L1/L2 |
| 校验自己的检测函数是否被 hook（自校验） | 用不写字节的 hook（异常 hook / GOT） | L4 |
| 用 raw syscall 读 maps | inline hook syscall 指令 | L3 |
| 多进程互相校验 | 每个进程都注入模块（LSPosed scope 全选） | L1 |
| 检测到异常直接 abort（不给 hook 机会） | 内核层阻断 abort/exit_group | L4 |
| 服务端二次校验 | 只能改上报数据，或在服务端侧解决 | 业务层 |

## 七、通用性的边界（诚实说明）

需要明确：**没有"一次编写永久通杀"的模块**。能做到的是：

1. **按观测面分类**——遇到新检测，先判断它落在 A~F 哪一面，
   再套用对应破解路径，不需要见过它的代码；
2. **按形态识别**——不认类名、不认包名，认"返回 JSON 数组的检测方法"
   这种结构特征，所以换一个 App、换一套检测体系照样能用；
3. **分层兜底**——L1 打不穿的交给 L2/L3/L4，而不是死磕一个层。

做不到的是：完全预知对手未来的新手法。所以模块设计成**可扩展**：
新增检测方向时，在对应层加一个 handler 即可，不用重写。
