# 检测方向速查表

> 遇到一个没见过的检测器时，用这张表反推它的实现，再决定从哪打。
> 不需要先读它的代码——看它在做什么、或看它的行为特征即可归类。

## 第一步：先判断「结论流向」

这是决定成本的关键一步。问一个问题：

> **它算完之后，结论交给了谁？**

| 情况 | 你能做什么 | 成本 |
|---|---|---|
| 结论变成 Java 对象（String/boolean/List）返回 | 改返回值（L1） | 最低 |
| 结论写成文件 / 发到服务端 | 拦文件写入，或改上报数据 | 中 |
| 结论在 native 内部直接用于处置（kill/abort） | 只能往 L3/L4 沉 | 高 |

**绝大多数实现属于第一种**，因为检测结果通常要给 UI 展示、
或要回传给上层决定怎么处理。这决定了 L1 的性价比极高。

## 第二步：按观测面归类

### A · Java 运行时结构

| 特征 | 常见实现 | 打法 |
|---|---|---|
| 查 `de.robv.android.xposed.*` 类是否存在 | `Class.forName` | 让加载失败 |
| 看堆栈有没有框架帧 | `getStackTrace` / `StackWalker` | 过滤帧 |
| 数 ClassLoader 数量 | 反射 `LoadApk` / native 读 ART | 只有内核层，或不注入 |
| 看方法是否被改 | 反射 Method 修饰符 | 改用 GOT/异常 hook |

### B · 进程内存布局

| 特征 | 常见实现 | 打法 |
|---|---|---|
| 读 `/proc/self/maps` 找匿名 r-x | `open`+`read` 或 raw syscall | 走 libc 的拦 open；raw 的需 L3 |
| 找 `/memfd:` 映射 | 扫 maps | 同上 |
| 看 so 列表有无陌生项 | 扫 maps | 减小暴露面 或 过滤 |

### C · 代码字节

| 特征 | 常见实现 | 打法 |
|---|---|---|
| 函数序言 vs 磁盘 CRC | 读自己代码段 | 不改字节（GOT hook）或双映射 |
| 全 `.text` 哈希 | 同上 | 同上 |
| 扫描 inline hook 跳转指令 | 反汇编找 `B`/`BR` | 用异常 hook，不产生跨段跳转 |

### D · 系统调用行为

| 特征 | 常见实现 | 打法 |
|---|---|---|
| `ptrace(PTRACE_ATTACH, self)` | 自附加 | 拦 ptrace（L2） |
| `fork` 子进程反向 ptrace | 外部视角 | 拦 fork（L2） |
| `process_vm_readv` 跨进程读 | 同上 | 拦该函数（L2） |
| 检测 `/proc/self/status` 的 TracerPid | 读文件 | 过滤文件内容 |
| `prctl(PR_SET_DUMPABLE, 1)` 自开门 | 配合 ptrace | 拦 prctl（L2） |

### E · 环境与文件

| 特征 | 常见实现 | 打法 |
|---|---|---|
| `su` 二进制存在 | `File.exists` | 拦路径判断 |
| 调试器连接 | `Debug.isDebuggerConnected` | 返回 false |
| adb 端口 / 属性 | socket / `SystemProperties` | 拦对应 API |
| 模拟器特征 | 属性、传感器数 | 拦对应读取 |

### F · 结果与处置

| 特征 | 常见实现 | 打法 |
|---|---|---|
| 返回 JSON 数组 | 最主流 | 改 `status` 字段（L1） |
| 返回 boolean | 次主流 | 返回 false（L1，需上下文判断） |
| 返回命中列表 | 常见 | 返回空表（L1） |
| 直接 `killProcess` | 立即处置 | 拦调用（L1） |
| `System.exit` / `Runtime.halt` | 同上 | 拦调用（L1） |
| `abort()` / `kill(getpid(),SIGKILL)` | native 处置 | 只有 L3/L4 |

## 第三步：三个高频误判

**这些坑我自己踩过，记下来。**

### 坑 1：按方法名 hook，误伤业务

`checkPermission`、`isChecked`、`scanWifiList` 都带检测词，
但它们返回 false 会直接破坏 App 功能。

**正解**：名字只用于缩小观察范围；真正判定看**返回值结构**。
`[{"status":...}]` 这种形态才是铁证。

### 坑 2：拦截太宽，把模块自己搞崩

拦 `Class.forName` 时如果连自己模块的类也拦，模块会在第一次用到
内部类时抛 `ClassNotFoundException` 而自毁。

**正解**：拦截前先判断调用者是不是自己（看栈），是就放行。

### 坑 3：默认值猜错

「查不到信息就当可疑」是常见错误。在 hook 里这意味着
「判不出来就拦掉」，会大面积误伤正常调用（主可执行文件、JIT 堆都查不到名字）。

**正解**：判不出来就**放行**。宁可放过，不可误伤。

## 一份检查清单

拿到一个陌生检测器，按这个顺序做：

```
□ 1. 它的结论去哪了？(Java对象 / 文件 / 服务端 / 直接处置)
□ 2. 它读什么？(maps / 内存 / 文件 / 属性 / 系统调用)
□ 3. 它用什么读？(Java API / libc / raw syscall)
□ 4. 有几种处置？(提示 / 杀进程 / 上报)
□ 5. 有几处埋点？(单点可删，多点要批量)
□ 6. 有没有自校验？(检查自己是否被 hook)
```

1-3 决定打哪层，4-6 决定打几个点。
