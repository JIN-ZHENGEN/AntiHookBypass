v3.3: hunter SIGSEGV 真修好（maps 视图合并 linker64 碎片段）

本轮把 hunter 的崩溃彻底归因，两个崩溃是两个独立问题。

## 一、SIGSEGV（真修好了）

崩溃指令 LDR q16,[x23,#0x410]，x23 = 0x7422f30000。
该地址恰好等于 [anon:.bss](7422f0a000-7422f30000) 的结束地址，
一字节不差；x20 = 0x7422e27000 是 linker64 的一个 4KB r-xp 碎片段起点。

hunter 按段扫描 linker64 算读取窗口，而 lsplant 装 inline hook
会改页权限、把 linker64 拆成多个碎片段，碎片一多窗口就算过头。

修法：在 maps 视图里合并 linker64 相邻 r-xp 碎片段（只延长结束
地址，不新增行），真实内存不动。

判决证据：
  有过滤（注入成功）：SIGSEGV = 0，多轮稳定
  无过滤（注入失败）：signal 11 ×3，fault addr 恒为 0x7422f30000

## 二、jit_code_cache 断言（不是我们造成的）

Check failed: !ContainsElement(zombie_code_, code_ptr)

做了逐层二分，每轮都先确认注入生效（日志行数 > 0）：

  只开 L2         → SEGV=0 jit=1（3 轮一致）
  只开 L3         → SEGV=0 jit=1
  Java 三层全关   → jit=1
  native 全关     → jit=1（且 SEGV 回来）

而且更早的两次实测里，注入=0（模块完全没进去）时同样出现该断言。
四组互斥配置下都存在，据此判定与我们的注入无关。

崩溃线程栈：
  Instrumentation::InstallStubsForMethod → JitCodeCache::AddZombieCode
  at ChooseUtils.ChooseJvm(Native method)

是 ART 在给该方法装 JIT stub 时，发现 code_ptr 落在已回收区间。

## 三、顺带解决的工程难题：LSPosed 路径失配

每次 pm install -r 都会生成新的 /data/app 目录，而 LSPosed 记录的
apk_path 不会自动更新，结果是模块静默不加载（日志 0 行）。
这回不再需要用户去点开关：直接给记录路径建 symlink 指向当前
APK，注入立即恢复。脚本已固化，可重复使用。

这个坑之前踩过两次，每次都要麻烦用户手动刷新。
