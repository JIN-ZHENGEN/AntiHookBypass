# 安装与生效说明

## 当前状态

模块文件已放到设备：

```
/data/adb/modules/antihookbypass_zygisk/
├── module.prop
└── zygisk/
    ├── arm64-v8a.so
    └── armeabi-v7a.so
```

## 但不生效，原因

Zygisk Next 在**开机时**扫描一次模块列表，把结果缓存在：

```
/data/adb/zygisksu/modules_info
```

实测该缓存内容（不含我们的模块）：

```
zygisk_lsposed 64 fd=8 dev=fe:27 ino=06360355 sz=2113536
hma_oss_zygisk 64 fd=9 ...
oh_my_keymint 64 ...
inline_hook_spoof 64 fd=11 ...
zygisk_lsposed 32 fd=12 ...
hma_oss_zygisk 32 fd=13 ...
inline_hook_spoof 32 fd=14 ...
```

这三个模块在列，我们的不在。原因是缓存是启动时生成的快照，
运行期新增模块不会进入这个快照。

## 生效需要什么

**重启 zygote（等于重启设备）**。这是 Zygisk Next 的设计，
没有热重载入口：

- `zygisksu` 模块的 `action.sh` 只生成 bugreport，不重载
- `ksud` 没有 module reload 子命令
- `zn-nsdaemon-zygote` 是运行时命名空间守护，不负责重扫模块

本次会话你已明确禁止我重启设备，所以我没有做这一步。

## 你可以怎么验证

重启后，用下面命令确认模块被加载：

```sh
# 1) 缓存里应该出现我们的模块
su -c "grep antihookbypass /data/adb/zygisksu/modules_info"

# 2) 作用域内进程的 maps 应该能看到我们的 so
su -c "grep -c antihookbypass /proc/\$(pidof com.zhenxi.hunter)/maps"

# 3) 模块自己的日志（仅在 ZLOGE 位置）
su -c "logcat -d -s AHBZYG"
```

## 注意

`kScopePkgs` 里目前写死了两个包：

```c
"com.zhenxi.hunter",
"com.cshlolss.antihook.detect",
```

要扩到其它应用，改 `module/jni/module.cpp` 里的这个数组，
重新 `bash build.sh` 并覆盖模块目录里的 so，然后重启 zygote。

## 与 LSPosed 版共存

两个版本可以同时装，但**不要同时对同一个应用生效**：
LSPosed 版会加载 lsplant，Zygisk 版不会，两边对 libart 的状态假设不一致。
建议先只在 Zygisk 版作用域里放测试目标，确认稳定后再决定是否撤掉 LSPosed 条目。

## 热迭代：改作用域不需要重启

作用域已改为读 `scope.txt`，不再编进 so：

```sh
# 加一个应用到作用域（不重编、不重装、不重启）
su -c "echo 你的包名 >> /data/adb/modules/antihookbypass_zygisk/scope.txt"
# 然后重开那个应用即可
```

读取点在 `preAppSpecialize`：那时进程还是 zygote 权限，能读到 `/data/adb`；
到 `postAppSpecialize` 已被沙箱限制，读不到。

## 框架控制命令（实机确认存在）

`/data/adb/modules/zygisksu/bin/zygiskd` 实际是个控制器：

```
znctl start|stop|exit|status
znctl disable-zygisk <true|false>
znctl enforce-denylist <disabled|enabled|just_umount>
znctl memory-type <default|anonymous>
znctl linker <system|builtin>
znctl dump-zn [-sa] [--webui]
```

其中 `exit` 就是 `emulated-soft-reboot.sh` 里那一句。`stop`/`start` 是
官方给的控制入口，但**会杀死正在运行的应用进程**，本次会话没有执行。

## 迭代成本阶梯（实测与未实测分开写）

| 场景 | 操作 | 成本 | 状态 |
|---|---|---|---|
| 改作用域 | `echo 包名 >> scope.txt` + 重开应用 | 几秒 | 机制已实现，待重启后验证 |
| 改 so 内容 | 覆盖 `.so` + 重开目标应用 | 十几秒 | **未验证**能否被 zygiskd 读到新内容 |
| 新增模块 | `znctl stop` + `znctl start`（或重启） | 半分钟 | **未验证**，且会杀掉运行中应用 |
| 内核级改动 | 整机重启 | 一分多钟 | — |

## 关于 fd 的一个实测

`zn-daemon` 持有每个模块 `.so` 的打开 fd，且 fd 的 inode/size 与磁盘
**完全一致**（8 条全部核对过）。这意味着如果 zygiskd 在 fork 时是从这个
fd 传下去，那么**原地覆盖 `.so`** 有可能被读到新内容。
但这只是推断，没有实测，不能当成结论用。
