# 分层对抗方案

> 这份文档说明每一层「能挡什么、挡不住什么、什么时候该往下沉」。
> 核心原则：**能用上层解决就别往下沉**，越往下兼容性越差、风险越高。

## 为什么必须分层

Java hook 有一个硬边界：

> 它能改变「Java 代码看到的结果」，但改不了 **native 代码亲手读到的物理事实**。

| 检测动作 | 谁在做 | L1 Java | L2 PLT | L3 syscall | L4 内核 |
|---|---|---|---|---|---|
| 查 `Class.forName("...XposedBridge")` | Java | ✅ | — | — | — |
| 抓堆栈找框架帧 | Java | ✅ | — | — | — |
| 拿检测结论 JSON | Java 交界 | ✅ | — | — | — |
| `killProcess` / `exit` | Java | ✅ | — | — | — |
| `open("/proc/self/maps")` 走 libc | native | ❌ | ✅ | ✅ | ✅ |
| 内存 CRC（读自己代码段） | native | ❌ | ⚠️ | ✅ | ✅ |
| `ptrace` 附加自己 | native | ❌ | ✅ | ✅ | ✅ |
| `fork` 子进程外部回读 | native | ❌ | ✅ | ✅ | ✅ |
| **直接发 `svc` 绕过 libc** | native | ❌ | ❌ | ✅ | ✅ |
| 数 ART ClassLoader 链表 | native | ❌ | ❌ | ❌ | ✅ |
| 服务端二次校验 | 后端 | ❌ | ❌ | ❌ | ❌ |

**读法**：✅ 能做，⚠️ 部分能做，❌ 做不到。

## L1 · Java 层（已实现，默认启用）

**载体**：LSPosed 模块，纯 Java。

**覆盖**：D6 结果出口、D7 框架痕迹、D8 环境探测、D9 自杀处置。

**优势**：
- 零配置，装完即用
- 不增加 native 暴露面
- 兼容性最好（只动 Java 语义）

**局限**：
- 碰不到 native 直接读的物理事实
- 如果检测在 native 内部闭环并直接处置，完全无效

**实现**：`ShapeDetector`（形态识别）+ `ResultForge`（结果伪造）
+ `TraceHide`（痕迹压制）+ `KillGuard`（处置拦截）

## L2 · Native PLT/GOT（已实现，默认关闭）

**载体**：自编 so，经 LSPosed 的 `native_init` 挂到 libc。

**覆盖**：D2 读取路径、D3 maps 读取、D5 ptrace/fork。

**做法**：替换 libc 导出的 `open` / `openat` / `ptrace` / `fork` /
`prctl` / `process_vm_readv`。每个替换函数先判「调用者是不是检测逻辑」，
是才阻断，否则原样放行。

**关键取舍**：判不出来时**放行**，不判可疑。
一开始想「查不到模块名就当可疑」，实测会大面积误伤
（主可执行文件、JIT 代码堆都查不到名字），直接把宿主搞崩。

**局限**：
- 检测若用 `syscall(SYS_openat, ...)` 或内联 `svc`，绕开 libc，本层拦不住
- so 自身会出现在 maps 里，可能成为新的可疑项

**开启方式**：`NativeLayer.ENABLE_NATIVE = true` 后重新编译。

## L3 · Inline hook syscall（未实现，仅方案）

**要解决的问题**：L2 挡不住 raw syscall。

检测方写这种代码就绕过 L2：
```c
long fd = syscall(SYS_openat, AT_FDCWD, "/proc/self/maps", O_RDONLY);
```
或者更极端，直接内联汇编发 `svc #0`。

**做法**：在 native 层 inline hook `syscall()` 本身，以及在
`libc` 的 `svc` 指令位置下钩子。

**技术难点**：
1. **指令长度**：ARM64 定长 4 字节，相对好处理
2. **并发安全**：改写代码时要暂停其他线程（`tgkill` + 信号）
3. **自动评分/ELF 重定位**：需要完整的反汇编器判断跳转指令是否够用
4. **自校验对抗**：改了别人代码，CRC 检测立刻发现——
   所以 L3 必须配合「维持内存视图一致」（见下）

**替代思路（更优）**：
不做 inline hook，改用 **seccomp 过滤器**。`prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER)`
可以在系统调用层拦截，且不修改任何代码字节，CRC 检测天然通过。
代价是需要 `PR_SET_NO_NEW_PRIVS`，且 seccomp 只能「拒绝」不能「伪造返回值」，
适用场景是「阻断」而非「欺骗」。

## L4 · 内核层（未实现，仅方案）

**唯一能彻底解决 D1（ClassLoader 计数）与 raw syscall 的层。**

**载体**：KernelSU / APatch 的内核模块（`.ko`），或直接改内核源码。

**能做什么**：
- 在 `sys_openat` / `sys_ptrace` / `sys_process_vm_readv` 入口拦截，返回伪造值
- 在 `mmap` 层控制 `/proc/self/maps` 的输出内容
- 直接修改读内存的返回数据，做到「进程内看到的和磁盘一致」

**代价（这是我不建议轻易上的原因）**：
1. 需要 root + 支持的内核
2. 写 C 内核代码，调试靠 `dmesg`
3. 改错直接 bootloop，手机上难救
4. 与内核版本强耦合
5. 内核模块本身会出现在 `/proc/modules`，有些检测专门查这个

## 沉层决策树

遇到一个打不过的检测，按这个顺序判断：

```
1. 它把结论交回 Java 层了吗？
   → 是：L1 改结论（最省力，先试这个）
   → 否：往下

2. 它读 maps / 读内存 / ptrace 走的是 libc 吗？
   → 是：开 L2
   → 否（raw syscall）：往下

3. 它算完直接处置（kill/abort），完全不经 Java 吗？
   → 是：L3 或 L4
   → 但它如果只是「阻断」而非「伪造」类需求，先试 seccomp

4. 它在数 ART 内部结构（ClassLoader 链表等）吗？
   → 是：只有 L4，或者考虑不用注入式 hook（从源头减少暴露）
```

## 一个反直觉的建议

**有时最好的方案是不 hook。**

检测方查的是「有没有注入」。如果改用不需要注入的方案，检测本身就失去意义：
- 用 `seccomp` 而非 inline hook（不改代码，CRC 通过）
- 用 GOT 覆盖而非函数体改写（不改 .text，字节扫描通过）
- 减少注入的类加载器数量（ClassLoader 计数正常）

这些「不做注入」的思路往往比「注入后如何藏」更彻底。
方法论里 D1、D4 的「首选」方案都是这个方向。
