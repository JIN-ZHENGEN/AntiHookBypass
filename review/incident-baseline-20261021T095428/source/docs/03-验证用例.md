# 验证用例：用样本做基准

> 拿 `AntiHook.apk`（包名 `com.cshlolss.antihook.detect`）当"考卷"，
> 逐项验证模块是否真的能绕过。这套验证方法同样适用于其他检测器。

## 样本的六项检测（已从源码确认）

| # | id | 实现文件 | 判定阈值 | 检测原理 |
|---|---|---|---|---|
| 1 | `native_classloader_count` | `artcount.rs` | `count > 10` 判 RISK | 数 ART `class_loaders_` 双向链表节点数 |
| 2 | `native_elf_libc` | `check.rs` | 内存 CRC ≠ 磁盘 CRC | libc 可执行段 vs 磁盘 PT_LOAD |
| 3 | `native_elf_libart` | `check.rs` | 同上 | libart 同理 |
| 4 | `native_anon_exec` | `scanner.rs` | 存在 <256KB 匿名 r-x 段 | 找 trampoline 落点 |
| 5 | `native_inline_hook` | `inlinehook.rs` | 有路径代码段→匿名段跳转 | 反汇编找 B/BL/ADRP+BR |
| 6 | `native_external_view` | `external.rs` | 子进程 ptrace 读到 CRC 不符 | fork + ptrace 外部回读 |

**关键结构**：六项全部由同一个 JNI 方法返回：
```
Java_com_cshlolss_antihook_detect_NativeLib_scan
  → 返回 [{"id","title","status","category","detail"}, ...]
```

**处置逻辑**（`Payload.act()`）：
```kotlin
if (risky > 0) {                    // 任意一项 status == "RISK"
    Toast(...)
    Thread.sleep(4000)
    Process.killProcess(Process.myPid())
    System.exit(0)
}
```
即：**只要 status 不是 RISK，六项全部形同虚设。**

## 验证步骤

### 步骤 0：确认模块生效

```bash
# 安装模块，在 LSPosed 里启用并勾选目标
# 启动目标 App，看日志
adb logcat -s AntiHookBypass
```
期望看到：
```
[AntiHookBypass] 已装载: com.cshlolss.antihook.detect (L2=false)
```

### 步骤 1：验证 D6 结果伪造

**观察点**：目标 App 首屏的六项结果。

| 项 | 未装模块 | 装模块后 | 说明 |
|---|---|---|---|
| ClassLoader 计数 | RISK（13-15 个） | **SAFE** | 结论被改写 |
| libc CRC | RISK | **SAFE** | 同上 |
| libart CRC | RISK | **SAFE** | 同上 |
| 匿名段扫描 | RISK | **SAFE** | 同上 |
| inline hook 扫描 | RISK | **SAFE** | 同上 |
| 外部视角 CRC | RISK / WARN | **SAFE** | 同上 |

**通过标准**：六项全 SAFE，且进程没有被杀（没有闪退）。

> 注意：本样本的 `detail` 文本会保留真实读数（因为 `forceSafe` 只改 status 字段），
> 所以可能看到"SAFE"配一段描述。这是刻意的——保留细节让结果看起来更真实。

### 步骤 2：验证 D9 处置拦截

**做法**：把 `ShapeDetector.forceSafe()` 临时改成直接返回原始值（关闭结果伪造），
只留 `KillGuard`。

**期望**：界面显示 RISK，但**进程不退出**，日志里有：
```
[AntiHookBypass] 拦截 killProcess(自身)
[AntiHookBypass] 拦截 System.exit(0)
```
这一项证明兜底层独立有效。

### 步骤 3：验证 D7 痕迹压制

在目标 App 里手动触发类确实存在性检查（或写个小 hook 观察）：

```java
// 期望：抛 ClassNotFoundException
Class.forName("de.robv.android.xposed.XposedBridge");

// 期望：返回 0
XposedBridge.getXposedVersion();

// 期望：栈里没有 de.robv.android.xposed 的帧
new Throwable().getStackTrace();
```

### 步骤 4：验证注入场景（通杀能力）

这是**最关键的验证**——它检验模块是否真的不绑包名。

1. 用样本 App 提供的"注入"功能，往任意一个 App（例如一个普通记事本）注入检测
2. 注入产物安装后，在 LSPosed 作用域里勾上那个 App
3. 启动它

**期望**：那个 App 正常启动，不弹"检测到hook环境"，不被杀。

**原理**：模块是按「返回值形态」识别的，不认识包名。
注入产物里的类叫 `com.cshlolss.antihook.detect.Payload`、方法叫 `scan`，
但模块不需要知道这些——它只在看到 `[{"status":...}]` 形态的返回值时才动手。

### 步骤 5：验证 L2（可选）

打开 `NativeLayer.ENABLE_NATIVE = true`，重编译安装。

**验证方法**：在目标进程里执行：
```c
// 期望：open 失败
int fd = open("/proc/self/maps", O_RDONLY);
```
但只有来自检测模块的调用才会被拦（模拟它自己的 `maps.rs` 走 libc 的路径）。

**注意**：样本的 `maps.rs` 用的是 **raw syscall**（`SYS_openat`），
所以 **L2 对它的这一条无效**——这正好演示了 L2 的边界。
那个情况下要靠 L1（改结论）或 L3。

## 覆盖矩阵

| 样本检测项 | L1 单独 | L1+L2 | 说明 |
|---|---|---|---|
| ClassLoader 计数 | ✅ 拿下 | ✅ | 结论交回 Java |
| libc CRC | ✅ | ✅ | 同上 |
| libart CRC | ✅ | ✅ | 同上 |
| 匿名段扫描 | ✅ | ✅ | 同上 |
| inline hook 扫描 | ✅ | ✅ | 同上 |
| 外部视角 CRC | ✅ | ✅ | 同上 |
| （隐藏）raw syscall 读 maps | ⚠️ 只能改结论 | ⚠️ | L2 也拦不住 svc，需 L3 |

**结论**：这个样本 L1 就全拿。因为它把结论交回 Java 层了。

## 如果打不过，怎么排查

按顺序检查：

1. **模块有没有加载**：`logcat -s AntiHookBypass` 有"已装载"吗
2. **是不是 LSPosed 作用域没勾**：模块要勾上目标 App
3. **检测是不是在 native 闭环**：看它有没有经过任何 Java 方法返回结论
4. **是不是 raw syscall**：反编译它的 so，搜 `syscall` / `svc`
5. **是不是 seccomp/内核级**：基本只能上 L4

## 反例：什么情况下这套会失效

诚实列出边界：

- **检测完全在 native 内部闭环，算完直接 `kill(getpid(), SIGKILL)`**
  → L1 完全无效，`kill` 是 syscall 不经 Java，必须 L3/L4
- **检测用 raw syscall 读 maps**（本样本就是这样）
  → L2 拦不住，但 L1 仍能改结论（因为结论最终还是回了 Java）
- **检测对自身做完整性校验**（检查自己的检测函数有没有被 hook）
  → 需要 L4 + 内存视图一致
- **服务端二次校验**
  → 客户端改不了，只能在协议层解决
